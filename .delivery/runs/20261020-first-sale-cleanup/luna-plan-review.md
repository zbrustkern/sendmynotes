## Critique of `local-draft.md`

The draft has the right small-scope intent and correctly protects the admin overhaul, analytics, pricing, ad setup, and fulfillment. It also recognizes rollout-trigger risk and asks for staging verification before production. I would tighten it in these ways before reserving the sprint:

1. **The factual-copy inventory is incomplete.** In `origin/main`, the privacy policy asserts 120 lb archival stock; the scenario landing page says “premium heavyweight”; public order-status copy gives a 2–4 day estimate; the `/send` page says the journey takes 60 seconds. Other production source has 100/120 lb wording in the Vending Machine Builder and V3 target experience; `lib/product-facts.ts` calls the envelope “matching,” which is not verified for this API SKU. The draft should require a route/feature-flag inventory and classify each hit as active, unreachable, or out of scope instead of treating one flow/policy search as complete.
2. **“Tracking claims” needs a precise definition.** The canonical specs allow order/fulfillment status and returned tracking data while rejecting blanket tracked-delivery or confirmed-receipt promises. Preserve conditional tracking numbers/links and status UI. Do not remove legitimate status functionality or make a policy promise stronger than supplier evidence.
3. **The source-of-release rule should be explicit.** “Apply the reviewed patch to a clean staging integration checkout” can still invite dragging the admin overhaul or staging-only state into production. Require a production-based candidate and cherry-pick/patch promotion after staging, with the admin overhaul excluded by path and commit ancestry. Compare the hosted revision and release trigger before push.
4. **Admin wording should keep evidence classes separate.** The Oct 11 baseline is historical canonical context, but its current notice exists in staging and is absent from production. The new Oct 20 statement is founder testimony. On production, use a dated static note with its own evidence label; do not claim it is adjacent to an existing banner, hardcode a “current zero,” alter orders/events, or treat testimony as a reconciled dashboard result. The exact text above is narrow enough if it can be inserted without the in-progress overhaul; otherwise omit it.
5. **Acceptance should identify observable checks.** Add explicit 320px/390px checks for full title/description and action visibility, keyboard focus/tap target, no layout overflow, and chooser open/close without triggering generation. For delivery copy, check both normal and status-present paths so a valid returned tracking number remains visible while absent tracking never implies tracking exists.
6. **The tests and checks are broader than this change needs.** Existing relevant checks, typecheck, and build are reasonable release gates, but avoid adding copy-mirror tests or unrelated end-to-end purchase scenarios. The visual check should verify source behavior at narrow and desktop sizes without placing a real order.
7. **Treat copy scope by consumer, not token.** “tracking” also appears in CSS class names, Google Ads setup, supplier payload handling, and order-data fields. “Artwork” occurs in prompts and rendering code. Exact active customer wording should be edited in context only.

## Release and failure risks to carry into the sprint

- A provider deploy may trigger automatically on branch push, before the pinned staging verification. Confirm deployment policy and use the approved explicit deploy mechanism.
- Admin route has extensive concurrent work on staging. A seemingly tiny edit can import newer component/schema assumptions; isolate by retaining the existing production admin shape and touching only the dated static note if feasible.
- Removing generic tracking language can accidentally remove real status visibility or conditional returned tracking data.
- Updating only one 100/120 lb variant leaves contradictory claims on another route or policy. Conversely, global replacement can alter historical documents and product prompts.
- “Mail in 60 seconds” may be read as dispatch/transit timing. Replace only sender-facing product claims that are live; do not present the correction as measured evidence of faster/slower use.
- A staging pass is not production evidence. Record deployed commit, hosted revision, and rollback source separately for both environments.
