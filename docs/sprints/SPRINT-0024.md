## Use cases
1. Signed-in menu → Account/Address book → inspect exact previous card front, message/style and address snapshots; copy into a new editable draft without paying/sending.
2. Explicitly save a generated front, retain an upload source or composed front, then reuse exact saved artwork without regeneration. Sources return to the existing Studio, not directly to print.
3. Save a person with an optional address and multiple dates; choose them in the builder; save/import updates deliberately without altering old orders.
4. Opt into a sender email 14 calendar days before an event, see its next date/time, pause individually/globally or unsubscribe; no automatic card sends.
5. Save/resume a durable account draft with conflict recovery; edit default personal return address and account preferences; submit genuine privacy requests with honest status.

## Architecture and frozen contracts
Parent owns `lib/account/contracts.ts`, `http.ts`, `client.ts`. Domain lanes may propose additive changes, but do not edit those files concurrently. Types: `AccountContact`, `AccountOccasion`, `AccountPreferences`, `AccountImage`, `AccountImageSelection`, `AccountDraftContent`, `AccountDraft`, `AccountActor`.

Shared server exports: `requireAccountActor(req, write=false)`, `AccountError(code,message,status)`, `accountJson(data,status)`, `accountError(error)`, `PRIVATE_HEADERS`, `accountCollection(kind)`, `accountDoc(kind,uid,id)`, `accountScope(uid)`, `validAccountId(value)`, `readAccountBody(req)`, `expectedVersion(input)`. Private records use server-derived owner UID/scope and environment-specific hashed keys. Top-level per-record collections work with the existing Firestore test adapter; no growing user arrays. Store `ownerUid` and `ownerScope` server-side, never trust client fields. Responses explicitly project public fields, never object keys, guest view tokens or payment internals. Production refuses mock persistence.

HTTP: single/create/update `{data:T}`, list `{data:T[],nextCursor:string|null}`, errors `{error:string,code:string}` with appropriate HTTP status. POST/PATCH/DELETE same-origin plus Firebase bearer; all reads owner scoped. New record version 1; edits/deletes include `expectedVersion`; conflict returns 409 without overwriting. Client `accountFetch<T>(user,path,init)` returns full parsed envelope and throws structured error. Every async UI result must be captured/keyed to UID and discarded on identity change. Page limit 20, maximum 50, validated opaque cursors, bounded server reads and explicit no-results vs failed-request states.

Lane 3 exports `getAccountPreferences(actor:AccountActor):Promise<AccountPreferences>` and `saveAccountPreferences(actor,input)` from `lib/account/preferences.ts`. This is the sole canonical global reminder pause/timezone source; Lane 1 consumes it. Settings stores only a verified identity-derived reminder destination and confirmed IANA zone; identity email changes invalidate pending destination assumptions. Until external delivery configuration is active, UI says reminder delivery is not active; dates/consent can still be managed.

Lane 3 owns `app/account/layout.tsx` and `components/account/AccountShell.tsx`, default export accepting `{children:React.ReactNode}`. Layout wraps every account page exactly once. All lane screens use the shared shell's spacing and `.account-*` styles or equivalent Tailwind warm paper/green palette. Shell provides authentication gate, actual signed-in email, sidebar and mobile Account pages disclosure. Lane 1 uses `components/account/people/**`; lane 2 uses `components/account/library/**` and `components/account/drafts/**`; lane 3 uses remaining shell/history/settings components.

Lists and detail route families: `/api/account/people`, `/occasions`, `/images`, `/drafts`, `/history`, `/preferences` with owner-checked `[id]` children. Client pages `/account/{history,people,dates,images,drafts,settings}` plus details. All content is real account data; no fixture/demo records ship.

### Library and drafts
Lane 2 owns durable private library copies under a separate `account-library/` object prefix, outside Studio cleanup traversal. Copy plus record commit must finish before success; orphan failures must be reclaimable. Explicit source save retains source alone; separate front save retains immutable front. Removing either does not delete the other, a referenced active draft or an ordered master. New account library policy: saved until removed; 100 saved items/account and existing 15 MB source limits, with real quota/error copy. No broad invite expansion. Source reuse copies bytes into a fresh authorized Studio source; accepted library front reuse validates owner/hash and active grant if upload-derived. Existing unsaved Studio TTL remains unchanged.

Generated results get a high-entropy short-lived save capability separate from cache ID; hash at rest, atomically bound to one UID on claim, idempotent same-owner replay. No arbitrary client URL fetch; source URL is server-held and allowlisted/bounded. Verified sign-in is required to save. Preserve result through optional sign-in; canceling save does not block guest sending.

`AccountImageSelection` is `{imageId,version,masterSha256}`. `POST /api/account/images/[id]/reuse` returns `{data:{draft:AccountDraft}}` for a front or `{data:{studioUrl:string}}` for a source. Front draft contains `content.accountImage` and no persistent private URL; parent loads preview via authenticated image-media route. `/api/account/images/[id]/media` returns owner-authorized bytes; `/resolve` returns safe metadata/selection only. Lane 2 may extend `lib/upload/order-master.ts` narrowly to recognize `body.accountImage`, validate it through library service, and pin its bytes into the existing immutable order copy. `body.frontImageUrl`, `uploadDesign` and `accountImage` are mutually exclusive. The remaining checkout/fulfillment flow stays unchanged. Parent adds builder payload support and UID clearing. Both granted-upload and ordinary generated library fronts must work; a generated front must not accidentally require an Upload studio grant.

Drafts store only `AccountDraftContent`, never quotes, payment state, guest access tokens, blob URLs or private keys. Explicit save/import, optimistic concurrency, rename/delete/duplicate, 90-day inactivity retention with UI copy and expiry checks/cleanup. `POST /api/account/drafts` accepts `{title,content}` and idempotency header, PATCH accepts `expectedVersion`. Parent builder resumes `?accountDraft=<id>` only after owner validation and explicit Replace current draft / Keep current draft decision. Resume resets schedule, quote, discount, acceptance and checkout state; query is removed after apply/cancel. History similar-card uses the same draft API and revalidates the recipient. Date/contact links use `?accountContact=<id>&accountOccasion=<id>`; parent resolves authoritative data and requires explicit application to existing work.

### People and reminders
Contact create needs displayName only. Address is optional; repeatable migration maps savedAddresses IDs deterministically, embedded occasions map to stable IDs with reminders off when prior affirmative consent cannot be established. New UI never writes old arrays. Legacy writers must not erase or resurrect new contacts; parent retires/bridges them after migration with clear version conflict behavior. Import previews create/update/skip and reports partial errors; never silently enables reminder email.

Occasions have month/day, annual/once, optional original/year, Feb 29 policy and per-event opt-in off by default. Validate real dates, same-day/past cases, year crossover and IANA local-time 9 a.m. minus 14 calendar days across DST. The approved design DOES include a separate optional tomorrow reminder for newly added events less than 14 days away; preserve that explicit choice. One-off dates require a year. Default leap-day mapping February 28, selectable March 1. Do not infer an event was handled from a name match.

Worker state machine: deterministic owner/event/occurrence/channel ID; pending → claimed with event version/lease → dispatching → accepted/failed/uncertain. Pauses/edit/delete/unsubscribe that win before provider invocation cancel stale claims; already in-flight mail cannot be recalled. Provider uncertainty is held for reconciliation, never blindly resent. Catch up at most 48h while event remains future. Recheck current consent, verified identity/email, global pause and timezone before dispatch. Email render is pure and transport injected; fake transport tests never invoke current real-email helper. Production adapter is default-disabled and requires configured worker auth, provider credentials and explicit activation; no false mock-send success. Unsubscribe uses an expiring high-entropy token hashed at rest. Unsubscribe GET is read-only confirmation, POST changes optional reminder state; scans do not unsubscribe. Emails contain no postal addresses or private notes.

## Definition of done
- Full responsive account experience matching mockup at 320/390/768/1024, keyboard/focus and auth deep-link return; no private data flashes or stale async responses on account switch.
- Authenticated history distinguishes loading, empty and failure; shows immutable front/inside/address evidence and true status, missing old fields gracefully. Make-similar never calls checkout by itself.
- Contacts with multiple dates/incomplete addresses, import and migration are versioned and owner-safe; new reminder consent off; editing/deleting cancels future applicable jobs.
- Library save/reuse and source Studio handoff persist exact private bytes; arbitrary IDs/URLs, foreign owners, stale hash, expiry and revoked grants rejected; explicit saved objects survive original Studio cleanup; duplicate saves do not duplicate quota.
- Account drafts save/resume across sessions, reject stale versions, preserve both edits on conflict, strip payment secrets and honor owner/asset lifetime. Existing device and guest flows remain functional.
- Reminder calendar/worker/opt-out/idempotency/error cases pass injected-clock/fake-transport tests. Actual email/scheduler activation remains an operational gate and is not claimed complete by local tests.
- Targeted tests plus appropriate regression suites, TypeScript and production build pass. Browser evidence uses synthetic records only. Any incomplete requirement remains explicitly open; do not mark sprint complete with required implementation missing.
