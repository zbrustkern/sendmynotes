# Sprint 0033 — Enforce discount limits and build bespoke code previews

**Revised November 19, 2026.** Close 33A independently after legacy parity and reservation recovery pass. Close Sprint 0033 after 33B delivers the operator workflow, wedding previews and ordinary single, international and multisend checkout. Track 33C as a separately accepted wedding integration dependent on Sprint 0031B. Its dependency does not hold the core release open.

## Pyramid Index

- **L0.** An operator can create a code for a specific set of cards, destinations or wedding projects and see exactly what a sender would pay and how much the campaign could spend.
- **L1.** Preserve legacy prices and repair reservations first. Version the scope and the discount separately. Use the same calculation in admin and checkout. Bind wedding redemptions to the paid project ledger.
- **L2.** [Rollout decisions](#rollout-decisions) · [Checkpoint A](#checkpoint-a--existing-limits-and-prices) · [Checkpoint B](#checkpoint-b--admin-authoring-and-preview) · [Checkout delivery](#checkout-delivery-in-33b-and-33c) · [Acceptance](#acceptance-matrix) · [Release and rollback](#release-and-rollback).

## Rollout decisions

**Customer limits are optional.** The founder chose to count new redemptions from rollout for everyone, including returning senders. Earlier redemptions contribute zero to a sender's personal count. Keep lifetime global uses and subsidy already spent. Save one cutover timestamp per environment and use authoritative settlement time, including successful $0 redemption, so webhook delivery time cannot move a purchase across the cutoff. Keep guest sending available for unrestricted codes. Require verified identity only for an offer with a sender restriction. Remove the implicit one-per-customer default from the welcome and VIP templates and show this setting explicitly in the editor.

**Configuration checked November 18.** A read-only inventory of production and staging found zero positive `perCustomerLimit` settings. Each environment returned three records from `offer_versions` and three from `discount_codes`. These collections can represent the same codes. The `WELCOME2` and `VIPGIFT` suggestions each specify one in the source presets. No existing code needs a personal usage backfill. [Admin presets](../../lib/promotions-and-growth-service.ts) · [Client presets](../../lib/promotion-client.ts)

**Wedding pricing follows Sprint 0031.** Both domestic and supported international envelopes advance a project's graduated base tier. Each international envelope adds $5. The displayed USD price includes any applicable tax, with no extra checkout tax in the pilot. Multisend v1 remains domestic, 2–25 cards. Wedding checkout supports 1–100 approved envelopes and requires the owner or a partner with current payment permission. ### Storage, migration and recovery contracts

| Record | Responsibility |
| --- | --- |
| Campaign | Lifecycle, current immutable policy reference and lifetime budget/use balance. Publish with a revision precondition. |
| Policy version | Append-only predicates, benefit, unit selection, ceilings and rounding. A quote pins this version. |
| Issued code | Unique normalized lookup, campaign reference, narrower scope and code-level balance. Use a keyed digest for private lookups. |
| Usage | Dedicated balances for campaign, code, project and verified sender as applicable. Use the canonical linked Firebase UID from a verified session for sender limits. Preserve it across provider linking and guest claim. A project credit follows its project across authorized payers. |
| Quote, reservation and redemption | Freeze allocations and exact counter deltas against the order and checkout revision. Allow one current hold and one settlement per order. Preserve old record IDs through a version-aware reader. |

Replace hardcoded v1 lookups in both admin APIs **and** the post-purchase grant issuer and availability reader. Retain issuance idempotency, link validity and original grant terms. Route legacy admin writes through a compatibility adapter that validates supported fields. The authenticated publisher owns policy changes and audit records.

**Expired holds.** Schedule a trusted reconciler every five minutes. Page at most 50 due holds per pass using an index on state and next-action time (initially the expiry). Claim with an expiring lease and revision, then inspect or cancel Stripe outside Firestore. A final transaction verifies the lease and applies the exact recorded deltas once. Release a confirmed canceled intent or a definitively unpayable attempt. Settle a timely verified capture even if its notification arrived late. For missing intent bindings, first reconcile idempotent intent creation. Retry uncertain results with backoff, retain exposure, and surface repeated failures with age and amount for operator review. Prove recovery after a worker crash, overlapping cron runs, cancellation racing capture and a quiet campaign with no subsequent checkouts.

**Settlement and refunds.** Remove both fulfillment-time legacy usage writes from the order processor. Make confirmation and webhook share a settlement step before dispatch. Expiry governs accepting payment terms. After capture, verify processor evidence of timing, amount, currency and binding. Quarantine genuinely late or indeterminate captures. Store each successful partial refund by processor refund ID and accumulate it once against frozen child and parent amounts, including multisend refunds. Test two distinct child refunds followed by duplicate notifications.

**Public validation.** Make code lookup and evaluation read-only. Create a durable quote only at checkout. Bound attempts per trusted network identity and session with a shared limiter. Exchange private links for an opaque session reference and clean the URL before analytics or referrer propagation. Keep raw private codes out of logs, attribution, telemetry and debugger results. Verify repeated previews create zero financial records.

## Checkpoint B — Admin authoring and preview

**Rule contract.** Publish an immutable policy version and keep campaign balances shared across versions and issued codes. The operator selects the workflow and price schedule, eligible recipient countries, minimum eligible quantity or spend, audience and time window. Separately they select the charge to reduce, the benefit (fixed once, fixed per eligible unit, or percentage), maximum units/cents per order or project, and campaign use/dollar limits. Use typed fields with explicit allowed values, integer cents and a deterministic remainder rule. New charge types require explicit selection. One code per order. A code can narrow a campaign's terms. Missing destination, identity or project facts cannot authorize a restricted discount.

**Operator journey.** Start at **Admin → Discounts → Create code**. Both `/admin?tab=discounts` and the existing promotions alias must reach it. Today's tab has its own form and API alongside a separate Promotions workspace. Wire the supported controls into the actual tab and route both admin write APIs through the same validated publisher. Preserve the current list, copy-link, pause and history actions.

1. Choose **Domestic multisend**, **International mailing**, or **Wedding project**. Name the campaign, enter or generate a code, and choose public distribution or a scoped private issue.
2. Set eligibility, select the card base or surcharge, then choose the benefit and ceilings. For wedding, select the project, eligible destinations and graduated price schedule. Show scope in plain language, including whether every envelope must qualify or only matching lines receive savings. Require a finite campaign budget for per-card, private-credit and free offers.
3. **Preview without reserving.** Use the checkout evaluator in a side-effect-free mode. Simulate a qualifying basket, a near miss and the largest permitted basket. Let the operator edit country, count, prior project purchases and prior allowance used. Show base, surcharge, eligible units, allocated discount, final charge, decline reason, and maximum subsidy per order and campaign. Identify synthetic project history in previews. Opening a link or preview cannot create a payable quote, hold, intent or mail order.
4. Save a draft, reopen it, preview it, then publish the reviewed revision. An intervening edit requires a fresh preview. Record the authenticated actor, environment, old/new version and reason. Show held, spent and remaining budget. Pause blocks new holds while existing payment outcomes settle under their original terms. A wedding code can be created, saved and previewed before 31B is ready. Until then the editor and publish API both explain why redemption is unavailable.

**Checkpoint B passes** when a tester can use the normal admin navigation to configure all three offers in the matrix below without editing JSON. The preview uses the same monetary result and reason codes as checkout. Include browser coverage for draft persistence, keyboard use, a stale preview, a failed condition and unavailable wedding checkout.

### Evaluator and operator decisions

Each product adapter returns a server-priced basket with workflow, schedule version, currency, trusted owner/project context and stable lines. Each line carries product type, canonical destination, optional project ordinal and components with stable ID, charge type, gross cents and tax policy version. A synchronous evaluator takes the pinned terms, basket, evaluation time and usage snapshot and returns eligibility, reason, allocations and totals. Registering a new charge type leaves existing allowlists unchanged. Test this with a synthetic add-on.

For capped units, select earliest eligible ordinal in wedding and stable server line order elsewhere. Resolve ties by stable line ID. Persist the strategy and an applied-promotions list of length zero or one on the order, quote and allocations. Reserve versioned benefit types for future fixed-price, tiered and buy-one-get-one offers. Defer those controls, stacking, and first-purchase eligibility until business rules and reliable history exist. A first purchase is distinct from a first use of a particular code.

From an existing campaign, issue one or a bounded batch of private codes sharing its budget. Retry issuance without duplicating codes. Clone rules into an inactive draft with a fresh budget, no issued codes and no history. An authorized operator can inspect a synthetic scenario or frozen order decision by ID, including policy version and decline reason. In the single-domestic preview, flag a net below the confirmed $4.88 supplier charge. Show $0.56 Stripe fees and $3.56 contribution only for the verified undiscounted $9 reference. Discounted fees and international or wedding contribution require separate evidence.

At publication and payment, validate the USD payable domain, including wedding ordinal 100+, supported counts, caps, mixed components and rounding. Check interior cases as well as endpoints. Reject unsupported or unprovable combinations. Test 0, 1, 49 and 50 cents. Only an expressly permitted domestic single promotional order may complete at zero. Keep demo fixtures independent of live campaign capacity.

## Checkout delivery in 33B and 33C

- **One basket and one frozen quote.** Build server-validated recipient lines with stable IDs and distinct card base and destination surcharge. Compute promotion eligibility and allocations after product pricing. In wedding batches preserve Sprint 0031's tax policy version and project ordinals. Carry policy version, basket revision, owner/project, gross, discount and net by component from preview through payment, receipt and refund. Fixed order reductions distribute across eligible components in integer cents with stable tie-breaking. Legacy orders keep their original child split.
- **Single and multisend.** The sender sees the savings and exact payable amount at Review & Pay for typed and linked codes. Requote if country, count, code or eligible lines change. Verify that resumed/replaced checkouts use the same owner, revision, currency, totals and hold. A code cannot make a suspended destination available. Keep the domestic promotional free route for supported $0 cases. Block publication of terms that can produce an unsupported zero or an unchargeable positive amount unless the displayed policy explicitly caps savings at a supported total.
- **Wedding.** Reuse 31B's authorized project, approved household revisions, prior settled ordinals and frozen payment manifest. Reserve project benefit units with the selected batch so two authorized payers cannot spend the same allowance. Evaluate only the eligible lines after tier pricing, and show the remaining project allowance for later batches. Recheck payment permission at checkout. Refund the frozen net for the specific envelope. Refunds and replacements cannot reset tier positions or replenish the code.

**33B sender experience.** Replace single-card client arithmetic in Review & Pay and multisend previews with server-returned components. A linked or typed code stays provisional while the sender can satisfy a missing condition. Map minimum quantity to “Add one more eligible card,” unknown country to “Choose a destination,” and identity required to “Verify to use this offer.” Preserve the complete draft and pending code through verification, cancellation and return to Review & Pay. Allow continuing at the shown regular price. For wrong country or workflow, explain the eligible purchase. For expired, exhausted or already-used offers, explain why savings ended. Use a generic unavailable message for private project mismatches. On mobile show card subtotal, mailing, savings and amount due together, with per-envelope details expandable and remaining wedding credit visible. Test keyboard, 320px width, linked-code entry, sign-in return and country changes.

## Acceptance matrix

Use synthetic codes and recipients. Dollar limits here are fixture values.

| Test | Expected result |
| --- | --- |
| **Legacy single and batch** | A legacy $2 code makes a domestic $9 card **$7**. Legacy 20% on five domestic cards makes **$43.20**, allocated **$8.64 each**. Base-only 100% leaves **$5** on an enabled international single and **$36** on five domestic cards. An eligible domestic free single uses the existing $0 completion path exactly once. |
| **Customer and budget cutover** | A prior customer with one pre-cutover redemption and a new customer each get one post-cutover use of an explicitly once-per-sender code. Each second attempt is declined. A guest can still redeem an unrestricted public code. Concurrent orders, two issued codes on one campaign, and two policy versions cannot exceed the final $5. A repeated release or webhook changes the counters only once. |
| **Bespoke multisend** | For 20% off 5+ domestic card bases, capped at $9, four cards pay **$36** with a quantity explanation, five pay **$36** with $9 savings, eight pay **$63**. Switching to a single or a wedding batch removes eligibility. |
| **International surcharge only** | For $3 off one eligible Canadian single's surcharge, preview, review and payment show **$9 + $5 − $3 = $11**. Switching to US shows **$9** and $0 savings. Missing country prompts for the destination. A disabled destination remains unavailable. |
| **Private wedding project** | $1 off each of the first 25 eligible bases in one named project. Fifty domestic envelopes pay **$352.50**, whether bought together or as 20 then 30 (**$145.00 + $207.50**). The second batch receives only $5 in credit. A different project, an editor without pay permission, held rows and replacement cards consume zero allowance. |
| **Mixed wedding and refund** | With the same credit extended explicitly to all destinations in the 31B mixed fixture, 98+2 pay **$698.50 + $18.50 = $717.00**. All 100 together also pay $717. Each of three international envelopes carries its $5 surcharge. Refunding the international envelope at position 99 returns **$12** once. The underlying no-code control remains **$742**. |
| **Settlement, migration and admin** | Exercise v1/v2 orders side by side, paused or edited offers with a payable hold, retry after cancellation, timely capture delivered late, and an uncertain outcome. Assert one capture/redemption per order, no duplicate dispatch, and sum of net lines equals captured amount. Validate admin permissions, environment isolation, idempotent publish, and no financial writes during previews. |

1. Extend the existing offer-engine, promotions workspace, post-purchase, checkout-resume, multisend, international, payment-discount browser and wedding pricing suites. Add emulator coverage for transactional contention and browser coverage through the real admin route. Compare the two engines on synthetic legacy orders before switching the writer. 2. Verify A independently. Enable B and the first budgeted multisend and international test campaigns on staging. Test authoring from the visible admin tab and compare preview, sender review, payment and refunds. Use Stripe test mode and held fulfillment throughout.
3. Keep wedding authoring and preview usable while 31B is pending. Mark wedding redemption accepted only after its permission, mixed-batch, concurrency and refund checks pass against the integrated staging build. Save sanitized acceptance evidence under `docs/sprints/evidence/SPRINT-0033/` during execution.
4. If a new workflow misprices or overspends, disable its new reservations and publication. Continue reading original policy versions and settling or reconciling outstanding holds. Keep the corrected limit enforcement in place. Activate production campaigns through a separate rollout decision.

**Definition of done.** 33A closes on the legacy, migration, budget, recovery and settlement gates. 33B closes on admin authoring for all three templates, synthetic wedding preview parity and the single, multisend and international checkout gates. 33C closes separately when 31B passes on staging and both wedding payment/refund matrix rows pass. For each release, published rules reproduce their admin previews to the cent, migrated limits reconcile, and a reviewer can trace one order and refund to the same frozen terms. Record the build revision, capability flags and test payment mode. Separate funded promotions, independent paid orders and studio comps in reporting.
