# Sol A critique of Sol B draft

## Strong ideas to retain

- The draft identifies the mounted `/new` seam, `EntryCardStep`, legacy local-draft hydration, and both paid/free order paths. Its explicit server-side master-byte resolver addresses the highest-risk existing `frontImageUrl` behavior.
- Typed contracts, exclusive Luna file ownership, a contract-freeze step, and main ownership of checkout integration make parallel work practical. The provider adapter's typed refusal/unavailable/unresolved outcomes prevent a misleading fallback.
- It treats expressive lettering, physical print tolerances, and customer conversion honestly; the provider capability still needs a bounded live synthetic test even though current Google documentation describes `generateContent` image editing with text plus `inlineData` for `gemini-nano-banana-2.1`.

## Contract ambiguities to settle before fan-out

1. **Upload checkout payload is internally inconsistent.** The draft says `uploadDesign` is accepted “alongside legacy `frontImageUrl`, never both,” then proposes a sentinel `frontImageUrl`. Freeze a discriminated `front.kind` or equivalent. For `kind:'upload'`, reject any client artwork URL, derive the order's private master key server-side, and adapt legacy non-upload orders separately. Show how the existing `if (!frontImageUrl)` guard changes in both paid and zero-price branches.
2. **Auth and handoff need one source of truth.** `UploadSelection` lacks a draft ID or handoff claim. Local `SelectedDesign` may be edited or restored from another signed-in account. Specify acceptance response, draft binding, and `/new` hydration behavior: UID-bound accepted design/revision/hash verified by the server on resume and at checkout; private preview fetched only after current account verification. A short-lived handoff claim or server draft binding would make the note-step transition deterministic. Clarify whether the builder accepts a local selection before server verification and what it displays while checking.
3. **Composition records are conflated with designs.** `UploadComposition` contains `designId`, while the route creates composition revisions and `/designs/:id/accept` refers to a design before acceptance. Define immutable composition ID, mutable candidate revision, and accepted design ID separately. Specify which hash and revision the acceptance request compares, and how an edit invalidates prior acceptance without overwriting an order-pinned master.
4. **Idempotency fields vary.** Generation body has `operationId`, other mutations use `Idempotency-Key`, acceptance also includes `idempotencyKey`. Choose one wire convention and state replay semantics. Persist provider operation state before calling; distinguish retry of an unresolved timeout from a new generation so neither allowance nor provider spend is silently duplicated.
5. **Owner capability binding is underspecified.** Existing admin session identifies email, while upload grants identify Firebase UID. Define how the founder-only `upload_access:manage` and `upload_standards:publish` capabilities are configured and checked against a verified admin actor. Do not let generic admin allowlist membership confer them. Account lookup should require verified email status, including ambiguity handling.
6. **Service exports assume records not yet defined.** Lane B needs `putDesign`, `getDesign`, private master reads, quota commit/release, and safe status transitions. Freeze the storage record shape, transaction ownership, and error mapping before workers start. In particular, Lane A should own generation reservation/state persistence, while Lane B owns provider execution and composition; define the handoff so a crash leaves a resumable status.

## Completeness and feasibility gaps

- The approved experience requires a 40-grapheme, at-most-three-line initial lettering limit, up to three successful versions, image prompt up to 1,000 characters, 20/day default, and 30-day default grant. The draft need not canonize defaults, but the plan should either specify these beta defaults or explicitly document a justified change. It also needs prompt-versus-exact-text conflict handling before generation, rather than letting the model render requested words into the illustration layer.
- Publishing standards needs a concrete state machine: editable draft → synthetic test evidence and human visual review → immutable publish/activation; restore creates a new activation event. Clarify how enabled treatments and default treatment are versioned with guidance and how existing generations remain pinned.
- Retention is mentioned only as cleanup. Specify abandoned quarantine ≤24 hours, seven-day unaccepted results, thirty-day accepted unordered design, and separately documented ordered-master retention or a reasoned revised policy. Define early deletion and account deletion behavior without deleting an order-pinned master.
- Preview delivery via bearer-authenticated blob is sound, but storage access must also fail closed against public bucket ACLs/download tokens, cross-account reads, and cache/log leakage. Add an explicit private-storage configuration check to staging gates.
- The provider document now confirms a viable `generateContent` image-input shape, so the implementation sequence can name that adapter as the first candidate. A bounded synthetic call must still verify this account/model, output parsing, and privacy terms. Keep the existing text-only cascade outside upload.
- The plan says “ship only treatments that pass” while the approved beta asks for Playful stack, Gentle arch, and Classic serif. Treat all three as the release gate; if one cannot be made real and safe, report a scoped blocker rather than silently releasing fewer choices.
- Verification should explicitly test `complete-free-order`, `processPaidOrder`, webhook/confirm retry, and any admin-comp dispatch with the pinned master. Staging payment and supplier controls should be inspected from current runtime before deployment, and QA must not trigger any physical order.

## Recommended merge decisions

Keep Sol B's mounted-UI specificity and exclusive file map. Freeze one discriminated checkout contract, separate generation/composition/accepted-design identities, and define UID-bound handoff plus order pinning before implementation. Make retention, standards activation, all three typography treatments, and both checkout paths explicit Definition of Done gates. The approved scope and staging request already authorize implementation and deployment; no generic approval interview is needed.
