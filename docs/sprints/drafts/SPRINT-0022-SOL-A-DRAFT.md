# SPRINT-0022 Sol A draft: Private upload studio

## Pyramid Index

- L0: An entitled sender can turn a private reference image and exact expressive words into a validated, immutable card front, then carry it through the existing builder on staging.
- L1: Account grants and private assets; reference-image generation and deterministic lettering; authenticated handoff and order identity; founder controls and staging proof.
- L2: Architecture, Implementation Plan, and Definition of Done below; approved product behavior in `docs/proposals/2026-10-30-upload-card-front/DESIGN_SPEC.md`.

## Overview

Build the smallest coherent beta of the approved separate `/create/upload` funnel. The founder can grant an existing account access, edit and publish creative guidance, test with synthetic fixtures, and revoke access. The sender can upload JPEG/PNG/WebP, generate an illustration using the actual image as provider input, adjust exact optional lettering without another image request, accept the complete front, and enter `/new` at the note step. Public gallery and guest sending remain unchanged. The print master is the order artifact; private source bytes and preview URLs never become order authority. Staging release is authorized; live payment, physical fulfillment, production release, and customer communications are outside this sprint.

The current candidate at `d9a8929` has a text-only `lib/nano-banana.ts`, a publicizing path in `lib/image-optimizer.ts`, `SelectedDesign.source` limited to `preset|custom`, and checkout that trusts client `frontImageUrl` before storing it as `Order.frontImageUrl`. Paid processing and free-order paths later pass that URL to `fulfillHandwryttenOrder`. These are concrete integration hazards, not reusable upload contracts.

## Use Cases

1. Founder signs in to `/admin/uploads`, resolves a real Firebase account by exact email or UID, grants or revokes its scoped entitlement, and sees an audit event. Only configured upload owner capabilities can mutate grants or activate standards; ordinary admin access alone is insufficient.
2. Entitled account signs in, opens `/create/upload`, validates one private image, enters optional exact words such as `Thank You`, chooses Playful stack, Gentle arch, or Classic serif, adds optional image direction, and submits one reference-based generation. Empty direction uses the server default.
3. Sender sees the final 17:22 composition, compares source and result, revises words/treatment without spending an image request, refines the illustration from the original normalized source, selects one of up to three recent successful versions, and explicitly accepts a specific composition revision.
4. Accepted front enters the note step; changing front returns to the studio without losing note/address/offer/attribution. A preexisting draft receives an explicit replace-front versus separate-card choice. Checkout rejects stale, foreign, deleted, expired, or revoked upload designs.
5. Failure states preserve usable work: unsupported/corrupt media, no grant, quota, provider refusal/outage, layout failure, stale revision, and interrupted handoff never become a false success or an orderable image.

## Architecture and executable contract

**Trust boundary.** Firebase ID token verified server-side establishes `uid` for all upload routes. Never accept `userId`, owner UID, object key, provider URL, active standards version, or grantor from a request. Admin endpoints require verified admin session plus independent configured `upload_access:manage` or `upload_standards:publish` capability bound to the verified actor. Mutations check Origin/CSRF, runtime environment, idempotency key, and expected record version. Admin email lookup resolves Firebase Auth UID and verified email; no provisional email grant. A granted sender gains no admin, free-order, or discount authority.

**Shared types first.** Define `UploadGrant {uid,status,version,expiresAt,dailyLimit,usedDay,usedCount}`, `UploadAsset {id,ownerUid,privateKey,sha256,width,height,mime,status,deleteAfter}`, `UploadGeneration {id,ownerUid,draftId,assetId,state,idempotencyKey,standardsVersion,model,illustrationKey,illustrationHash,attempts,validation}`, `UploadComposition {id,generationId,revision,exactText,templateId,templateVersion,fontHash,layout,masterKey,masterHash,previewKey,validation}`, and `UploadDesign {id,ownerUid,compositionId,compositionRevision,masterHash,acceptedAt,state}`. Store environment in namespaced collection/object paths. Persist immutable standards versions and append-only activation/audit events. IDs are opaque; `masterHash` binds exact bytes. `SelectedDesign` gains `source:'upload'`, `uploadDesignId`, `compositionRevision`, `masterHash`; any `imageUrl` is display-only and must not be persisted as a durable private URL.

**HTTP boundary (all responses `Cache-Control: private, no-store`; typed `{code,message}` failures).** `GET /api/upload/access` returns `{eligible,expiresAt,remaining,resetAt,paused,activeStandardsVersion,treatments}`. `POST /api/upload/assets` accepts multipart image and idempotency key; returns `{assetId,width,height,mime,warnings,expiresAt}`. `GET /api/upload/assets/:id/preview` streams owner-authorized normalized pixels. `DELETE /api/upload/assets/:id` deletes unpinned source and dependent unused results with an explicit ordered-master exception. `POST /api/upload/generations` takes `{assetId,draftId,imagePrompt,letteringRegionTemplate,idempotencyKey}` and returns `{generationId,state}`; the exact words are submitted to composition, never to image generation as raster text. `GET /api/upload/generations/:id` returns state, error code, and `illustrationId` only on validated success. `POST /api/upload/compositions` takes `{generationId,exactText,templateId,expectedRevision,idempotencyKey}` and returns `{compositionId,revision,masterHash,previewPath,validation}`. `GET /api/upload/compositions/:id/preview` streams a derivative of the same flattened master. `POST /api/upload/designs/:id/accept` takes `{compositionId,expectedRevision,expectedMasterHash,draftId,idempotencyKey}` and returns `{uploadDesignId,revision,masterHash,handoffToken}`. Treat `handoffToken` as a short-lived, single-use server claim bound to UID/draft/design, not an artwork URL. `GET /api/upload/designs/:id` is ownership checked. Admin routes provide account resolve/list, grant/revoke and standards draft/test/publish/restore with expected versions. Their exact route organization may be adjusted, but request/response semantics should be frozen before lane edits.

**Atomic operations.** Upload validation checks 15 MB encoded size, decoded MIME, ≤40 MP, one still image, min short edge 512 px, bounded decoder work, orientation, sRGB, EXIF/GPS stripping, and transparent-pixel flattening. A sub-1000 px short edge warns. Raw quarantine bytes are purged after normalization; a cleanup job catches abandoned objects within 24 hours. Source, illustration, master and previews live in private Storage; avoid `makePublic()` and the existing image cache. Reads require UID ownership, and browser/account switches clear in-memory pixels. A generation transaction reserves one daily request and one concurrent slot by `(uid,idempotencyKey)` before provider work; duplicate requests return the same operation. Invalid files and pre-provider failures spend none. At most two provider attempts share the reservation; ambiguous timeout remains unresolved pending reconciliation. A failed new generation leaves earlier successful versions. Generation results are compared against current grant/version before release. Quota and pause configuration are operator controls, with no unadvertised narrower format or cost gate.

**Generation and composition.** Verify the current provider's image-input API and retention terms against primary documentation before implementation. The adapter must transmit normalized image bytes, locked 17:22 flat-art rules, selected immutable creative guidance, and the sender's lower-priority direction. Image content and sender text are data, never control instructions. Provider outage/refusal fails visibly; no text-only or raw-source fallback. Validate returned image decode and 17:22 crop/subject clearance, record model and source/output hashes. Use versioned, licensed local fonts and deterministic server-side shaping/rasterization for the three allowlisted treatments. Preserve Unicode graphemes and intentional line breaks; detect unsupported glyphs and overflow. Render exact text into a 1275×1650 flattened master (17:22) with a preview derived from that master. Layout record includes exact text, glyph positions, font hash, template version, bounds, color, and validation version. Contrast, overlap, and safe-margin checks are application heuristics, never supplier-certified trim claims. Admin guidance can tune art direction but cannot override locked standards or type code. Publish only immutable standards/treatment versions after synthetic tests and human visual review.

**Checkout identity.** `create-intent` accepts an upload design reference only in a distinct discriminated payload, for example `front: {kind:'upload',designId,compositionRevision,masterHash}`; it must reject any `frontImageUrl` submitted alongside `kind:'upload'`. Authenticate UID again, check grant active and design owner/accepted state, compare revision/hash, and pin the master on the order before Stripe intent or offer reservation wherever feasible; use an idempotent order transaction to prevent duplicate pins. For catalog/custom existing flows retain their current payload behavior. Store `frontKind`, `uploadDesignId`, `compositionRevision`, `masterHash`, private master key and owner UID on the order; never persist a preview URL as `frontImageUrl` for upload orders. Recheck at checkout creation; after authorized payment, revocation does not cancel an existing order. Both paid `lib/order-processor.ts` and `complete-free-order` must resolve the pinned bytes server-side, and `lib/handwrytten.ts` needs a bytes/file adapter that never fetches an arbitrary upload URL. In this staging beta, no call to these fulfillment paths is used as a check, and live-payment/supplier switches remain off.

## Definition of Done

- Synthetic account tests prove signed-out, non-entitled, cross-UID, expired, revoked, stale version, concurrent, and environment-crossing requests fail at every asset, generation, preview, acceptance and checkout route; grant/revoke/standards mutations are capability checked, idempotent, version checked and audited.
- Fixture tests prove JPEG/PNG/WebP acceptance and corrupt/animated/oversized/decompression rejection, metadata removal, private object ACL, early deletion and cleanup; neither analytics nor incident logs contain prompt, filename, exact words, source pixels or private URLs.
- Captured provider request proves image bytes are present with mandatory locked rules for empty and adversarial sender prompts. One or two bounded synthetic staging generations verify actual provider capability; failure never presents text-only or source image as a generated result.
- Composition fixtures include blank, large `Thank You`, long words, punctuation, accents, line breaks, unsupported glyphs, missing font, low contrast and occupied text region. Preview bytes derive from the hashed immutable master; stale revisions cannot be accepted or ordered. Changing words uses no image-generation allowance.
- Browser/component checks at 320, 390, 768 and 1024 px cover keyboard/focus/live announcements, access states, refinement, reload, account switch, three-version selection, and interrupted handoff. Existing note/address/review, return-to-studio, offer and attribution survive explicit draft choice.
- Checkout tests cover both paid and free paths with a pinned upload master, including revoked-before-checkout rejection and revoked-after-authorization preservation. No client URL or raw original reaches supplier path. Existing preset/custom checkout tests pass.
- Typecheck/build and focused security/component tests pass. Staging shows the exact deployed commit and founder-only entitlement; production remains untouched. Staging exercises no live payment, supplier order, or customer message. Findings distinguish founder tests from independent conversion (baseline zero).

## Risks and mitigations

- **Provider API/retention mismatch:** verify primary provider contract and privacy terms first; fail closed if image input or acceptable handling is unavailable. Do not infer support from text-only `nano-banana` cascade.
- **Large private image pressure:** streaming limits, bounded Sharp decode, Storage rather than Firestore blobs, private previews, durable operation state and cleanup. Quarantine deletion is part of success and failure paths.
- **Expressive text exceeds region:** use template-specific fit and glyph checks; expose shorter-word/treatment/recompose actions, never silent shrink, clipping, misspelling or fallback.
- **Checkout bypass via existing `frontImageUrl`:** discriminate upload order type, validate owner and hash server-side, reject mixed payloads, pin immutable bytes, and test paid/free/return paths. This is the highest-risk integration seam.
- **Parallel file collisions:** contracts frozen first, ownership as above, integration reserved to main. Review each lane against contract before merging.
- **Physical output unknowns:** 17:22 and 1275×1650 are verified geometry/current target; bleed and trim safe zone are heuristics pending supplier evidence. No quality guarantee or fulfillment test is inferred.

## Dependencies and Open Questions

Dependencies: Firebase Auth UID verification, private Firebase Storage bucket/service credentials and lifecycle behavior on staging; provider image-input API and retention documentation; licensed font files/shaping engine; existing staging payment/fulfillment disable flags verified from current runtime. If any is unavailable, report the concrete blocker and keep release founder-only without simulating a successful upload path.

Implementation decisions to settle during contract freeze: the exact provider endpoint/model and deletion guarantee; whether current Firebase Storage configuration supplies a private bucket without new infrastructure; font family and glyph/script allowlist; operational order-master retention policy and deletion wording. These do not require a new product approval if established from verified contracts and the approved design. Do not silently narrow approved JPEG/PNG/WebP, prominent lettering, or grant behavior to avoid the work.
