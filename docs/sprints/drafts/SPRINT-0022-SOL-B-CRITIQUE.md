# Sol B critique of SPRINT-0022 Sol A draft

Sol A captures the approved product and the main security boundary well. Its order identity, private-byte fulfillment path, owner-only grants, exact-text compositor, staged tests and no-supplier validation rule should survive synthesis. The following points need a concrete contract before Luna work begins.

1. **Make the `/new` handoff executable.** The candidate's `app/new/page.tsx` mounts `EntryPrototypeClient` directly and defaults to card selection. A short-lived single-use `handoffToken` is proposed, but the draft does not specify which endpoint consumes it, how it maps to a draft, or how refresh works after consumption. Prefer a server acceptance record plus a UID-bound, idempotent handoff claim that `/new` consumes once and can re-read by draft ID on refresh; define its expiry and failure state. Assign `app/new/page.tsx`, `components/flow/EntryCardStep.tsx`, and both `EntryPrototypeClient` hydration paths to Lane C. Verify `?step=note` cannot advance without the accepted selection loaded. This is a release blocker, not navigation polish.
2. **Use a discriminated draft type instead of the required `imageUrl` field.** Current `SelectedDesign` requires and persists `imageUrl`; saying an upload URL is “display-only” does not keep it out of `lib/draft/store.ts` or legacy local storage. Define `SelectedDesign = PresetDesign | CustomDesign | UploadDesign`, with upload carrying only opaque `designId`, `revision`, `masterHash`, title, and accepted state. Render via an authenticated fetch-to-blob preview held in memory; account switch/unmount revokes it. Migrate schema v1 and legacy local draft state without clearing notes, addresses, offers or attribution. The pending upload selection should never be hydrated as an accepted cover from a stale browser URL.
3. **Freeze one HTTP/checkout vocabulary.** Sol A uses `id`/`compositionId`/`uploadDesignId`, `templateId`, `masterHash`, and a `front.kind` payload. These are sound choices, but Lane C and main need exact response and error types rather than “route organization may be adjusted.” Decide whether `POST /compositions` creates an immutable revision on one design or a new composition ID each time; define acceptance as `{designId,revision,masterHash}` and make the checkout payload match that exact tuple. Standardize bearer token, `Idempotency-Key` header, expected-version field, 409 response, and no-store preview fetching. Keep private object keys and URL paths out of all JSON responses.
4. **Clarify cross-lane ownership and dependency order.** Lane A lists quota/access/storage; Lane B lists generation, composition and preview routes. A asset previews and B composition previews may share route names, and `resolveMaster` needs A's private object reader. Freeze `putDesign/getDesign/getPrivateMaster`, `reserveGeneration/reconcileGeneration`, and `validateUploadCheckoutSelection/readAcceptedMaster` signatures first. Assign all preview route files by exact path, all admin navigation files, and privacy copy to a single owner. Lane B can develop against typed fakes while Lane A builds services; main integrates only after both pass contract tests. No two Luna lanes should edit `lib/upload` barrels or a common route.
5. **Pin checkout before irreversible side effects, including the free path.** The draft rightly rejects mixed `frontImageUrl` plus upload design, but `create-intent` currently reserves offers and writes orders in paid/free branches. Specify the validation and pin sequence before offer reservation or Stripe creation, and decide how an idempotent retry returns the same order instead of creating a second intent or consuming another offer slot. `userId` in the existing request is client-supplied and must not establish upload ownership. The free path must share the same validator and pinned master. Paid confirmation and admin-comp processing must read the already pinned order rather than reselecting a mutable design.
6. **Provider shape can be narrower now.** Fresh Google documentation confirms `generateContent` image editing with text plus `inlineData` for `gemini-nano-banana-2.1`; the existing text-only cascade is still unsuitable. Name that adapter as the first implementation target, transmit normalized reference bytes and locked server instructions in the same request, and require a captured request plus one or two bounded synthetic staging outputs. Preserve a typed refusal/unavailable/unresolved outcome and do not fall through to text-only generation. Provider retention terms and live capability remain gates before launch copy or wider access.
7. **Turn visual checks into testable acceptance.** “Validate crop/subject clearance” and “contrast/overlap” imply stronger automated vision than the plan defines. Require deterministic decode, aspect, dimensions, glyph bounds, margins and measured local contrast checks; add explicit human review of representative original/result/master pairs for subject preservation, no mockup, no stray text and expressive composition. The three treatments must be visibly distinct, with a prominent `Thank You` fixture, while sharing a quiet region only where that actually works. Fail visibly on unsupported glyphs or layout; do not label a prompt rule as a guarantee.
8. **State retention and pause semantics at the API boundary.** Specify unaccepted asset/result expiry and ordered-master pinning, a cleanup job owner, and what early deletion removes. Differentiate a global upload-work pause from an active-grant check; an accepted front should remain usable during a new-work pause if the grant remains active. Define quota consumption for valid submissions versus pre-provider failures and unresolved timeouts, plus at-most-one concurrent job. Test revocation before checkout intent against authorization after a paid order has been created.

The proposed DoD is broad and appropriate. The synthesis should keep it but add a mounted `/new` browser proof with real server-authenticated preview, complete note/address/review state, and a byte/hash assertion that the accepted preview master equals the order's pinned master. Staging smoke should verify the deployed commit and safe payment/fulfillment runtime flags without calling supplier or fulfillment scripts.
