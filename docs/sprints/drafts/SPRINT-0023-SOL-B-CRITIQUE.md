# Sol B critique of SPRINT-0023 Sol A draft

## Strengths to keep

Sol A stays within the approved small menu scope, treats `/api/upload/access` as discoverability rather than authority, separates the administrator cookie from the Firebase sender identity, and protects the guest flow. Its state matrix, UID-bound async check, two draft hydration paths, and disjoint Luna file ownership are useful merge material. The DoD includes the right hosted and privacy checks without proposing a live charge or supplier call.

## Corrections and blockers to settle

1. **Update the baseline.** The latest root browser run passed initial handoff, same-tab refresh, and new-tab restoration of the accepted upload, private preview and checkout tuple. Sol A's overview and dependency section still call new-tab restoration an unresolved defect. Preserve that passing implementation and evidence. The remaining gate is signed-out/cross-UID behavior, including a late preview/access response after account switch. Repeat new-tab only if the privacy fix touches its path or a required release check demands it.
2. **Define one small identity-transition rule, not a new architecture.** On `user.uid` change or sign-out, immediately stop showing and revoke the old blob URL, hide the upload selection and block checkout; cancel/ignore prior UID requests. Keep safe note/address state, then offer the approved catalog-front or separate-card choice. Reopen the previous owner's private selection only after same-UID authentication and `GET /api/upload/designs/:id` validation. Apply this to the session draft and `smn_active_draft_v2*` legacy path; account-specific retained tuple data must never be treated as visible current state before verification. A request sequence or abort signal plus captured UID is enough.
3. **Keep lane B narrow.** Sol A assigns `components/upload/UploadStudio.tsx` to the draft lane, but the signed-out/cross-UID issue is in the mounted builder and both draft stores. Touch UploadStudio only if a concrete pending-upload leak is demonstrated. The current in-progress `app/preview/entry/client.tsx` changes must be integrated by that file's owner; no parallel editor should rewrite its passing new-tab work.
4. **Make sign-out failure states explicit.** Current `AuthContext.signOut()` deletes `/api/admin/auth` first and then signs out Firebase. Admin-cookie deletion failure leaves Firebase signed in and must show retry. Firebase sign-out failure after a successful cookie deletion leaves only the sender account signed in and must be reported honestly; the UI should not claim both sessions cleared. Keep this shared operation in `AuthContext`, and have both the menu and admin switch show its result rather than duplicating deletion calls.
5. **Specify the entitlement refresh trigger and UI states as the acceptance contract.** Menu-open, focus/visibility return and UID change should recheck, while auth loading must suppress signed-out flash. A failed `/api/upload/access` request is `error`, not inactive; expose retry. The account page should use the same active/checking/error distinction if it displays the Studio entry. No extra polling or global state framework is needed.
6. **Avoid broad admin rework.** Both authorized admin emails, `Upload administration` labels, and 401/403 separation are already in the working tree. Lane C should verify these exact behaviors and repair only failures. Administrator authorization remains separate from a UID Studio grant; forwarded mail is irrelevant to entitlement.

## Merge recommendation

Use Sol A's state matrix and lane outline, amended with the passing new-tab baseline and a focused signed-out/cross-UID browser scenario. Add a test where UID A's accepted cover is visible, sign-out occurs while a private preview request is pending, UID B signs in, and neither A's blob nor design tuple appears or reaches checkout. Pair that with guest-modal cancellation, admin-cookie/Firebase failure injection, grant error/retry, and 320/390/768/1024 keyboard checks. Main can integrate the already changed files and stage the exact commit once those focused gates, typecheck and build pass; no further product approval or architectural expansion is needed.
