# SPRINT-0024 Luna A critique of Luna B draft

Overall, B is a strong executable scope: it correctly recognizes the current Upload Studio and local draft limits, assigns all six destinations, and keeps reminder activation externally gated. Keep its user-flow, history-state, and broad acceptance detail. Before merging, tighten these contracts against the current code:

1. **Saved uploads must survive the actual cleanup path.** B says “intentional Save for later is the only action that can extend source retention,” but does not specify how that save protects bytes from current cleanup. Today upload assets/generations/designs expire after seven days; `cleanupExpiredUploads()` in `lib/upload/access.ts` deletes expired objects/rows and builds its live-object set only from `uploadAssets`, `uploadGenerations`, and `uploadDesigns`. A library metadata reference alone will not pin an object. Require an atomic save/pin contract (or a durable private library copy), explicit `savedAt`/`retainUntil` semantics, and cleanup changes that respect the pin and include library object keys in orphan detection. A save racing the cleanup boundary must either commit the pin before cleanup observes expiry or fail visibly without claiming “Saved.” Deletion must release only the library reference; preserve accepted order masters/snapshots. Keep this limited to explicitly saved owner assets and do not expand the invited grant or source quota by accident.

2. **Generated cache ID is not ownership proof.** Current `/api/generate-cover` is callable without account authentication, writes `image_cache_pool` rows without a UID, and returns `cacheId` plus an image URL. `resolveAdminCompAssetById()` verifies only that a globally cached generated item exists and is available/claimed; the ID proves provenance, not which sender generated or owns it. B's “existing server generation result ID” is therefore insufficient for `/api/account/images` to attach the result to the signed-in user. Add an unguessable, single-purpose result capability issued with the generated result and bound at save time to that result, or another auditable claim proof that remains usable if the sender signs in after generation. Consume/bind it transactionally to one UID, disallow cross-account re-claim, and copy/finalize the server-resolved bytes into private immutable storage. Never accept a client URL or treat a public cache URL as a private library asset. Keep ordinary guest selection working. Tests need stolen cache ID without capability, replay, two-account race, and cache expiration/deletion cases.

3. **Define reminder transition and cancellation races precisely.** B correctly requires a transaction/lease and rechecks, but “edit/pause/delete cancels pending work” can overpromise once a worker has claimed an occurrence. Make occasion version/consent, occurrence state, and dispatch claim one transactional state machine: schedule idempotently; claim only the current version; before provider invocation recheck version and opt-in; mutations invalidate pending claims. Define `dispatching`/`uncertain` outcomes: an opt-out that wins before claim guarantees no call; if the provider call is already in flight, mark/reconcile it and do not tell the user that cancellation can recall an email. If provider acceptance is unknown, do not blindly retry unless the configured provider has a verified idempotency/reconciliation mechanism; otherwise hold for reconciliation. The real provider capability stays an activation gate.

4. **Keep transport incapable of sending during local tests.** The existing `sendOccasionReminderEmail()` in `lib/email-alerts.ts` calls the Resend client directly when configured and has no injected transport; reusing it from a worker test can send actual mail. Separate a pure message renderer from an injected transport interface. Worker defaults to a rejecting/no-op transport outside explicit production activation; tests inject a fake and assert zero Resend/network calls. Do not run this existing helper as a reminder audit. Also review its current fulfillment-timing copy against canonical specs before reuse; the account reminder example does not need a delivery promise.

5. **Do not defer working surfaces behind the external gate.** B should state explicitly that all local account destinations, date CRUD/calendar math, outbox transitions, pause/unsubscribe UI, durable drafts, Studio library save/reuse, and fake-transport worker are implemented and exercised in this sprint even if production dispatch remains inactive. “Not active yet” is an honest runtime state, not a reason to leave the dispatcher, settings, or one of the six destinations as a placeholder. Keep only provider/scheduler/inbox verification, final retention policy confirmation, and production migration/activation outside the local acceptance boundary.

## Contract additions for the merged plan

- **Library reference:** `saved → ownerUid + source kind/id/version + immutable private object key/hash + savedAt + retainUntil + deletedAt`; reject if source is missing, expired, foreign, or no longer authorized. Pin/copy, metadata commit, and cleanup reachability must be ordered so there is no success response before durable retention is established. Reuse resolves the exact immutable rendition; no generation or external URL fetch.
- **Generated-result claim:** a result ID is lookup only. Require a high-entropy capability distinct from the ID, store only its hash, scope it to result ID and expiry, and atomically bind/consume to one verified owner. If the result is already a public provider URL, server must validate and snapshot it into private storage before account save completes. Never log capability, prompt, URL, or private image bytes.
- **Reminder state:** `pending → claimed(version, lease) → dispatching → accepted | failed | uncertain`, with `cancelled`/`missed` terminal for eligible rows. Event opt-out/version changes and lease claim transact against the same current occasion version. Idempotency key remains owner/event/occurrence/channel across edits/reverts. Treat accepted as sent, not delivered. A provider uncertainty without lookup/idempotency remains held, not auto-retried.
- **Scope:** all six account destinations and their local data paths are part of this sprint. External readiness may disable delivery only; it must not disable date management, draft saving, image library reuse, or read-only order history.

These findings come from source in the requested clean baseline: `app/api/generate-cover/route.ts`, `lib/firebase-admin.ts`, `lib/admin-comp-pricing.ts`, `lib/upload/access.ts`, `app/api/cron/upload-cleanup/route.ts`, and `lib/email-alerts.ts`.
