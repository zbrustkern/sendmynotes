# SPRINT-0024 Luna B critique of Luna A draft

## Strengths

- The draft is full-scope and connects all requested journeys: account overview/history, people with multiple occasions, saved fronts and uploads, reminders, settings, and durable drafts. It correctly treats these as mounted customer flows rather than mockup scaffolding.
- Its baseline notes match this clone: the invited Upload Studio already owns private source/generation/composition/acceptance, `lib/draft/**` is device-oriented, and the legacy account/reminder writes cannot be the new security boundary. It also catches the consequential seven-day source expiry and 20-active-asset cap.
- The frozen contract, per-record persistence, verified owner checks, idempotency/versioning, repeatable migration, and explicit consent migration are practical protections against data loss and accidental reminder sends.
- History stays read-only and snapshot-based; the draft distinguishes payment, fulfillment, and provider uncertainty. The reminder section includes local-time scheduling, outbox leasing, dedupe, unsubscribe scanner safety, catch-up cutoff, and fake-provider-only validation.
- The lane split is implementable and mostly disjoint: Lane 1 owns people/dates/reminders; Lane 2 images/drafts; Lane 3 shell/history/settings; parent owns shared contracts and builder/menu integration. The acceptance matrix is concrete and avoids real mail, payment, supplier, and fulfillment activity.

## Implementable fixes before dispatch

1. **Freeze complete UI ownership and shell API.** Lane 3 should explicitly own `app/account/layout.tsx`, the `/account` overview and `AccountShell`/mobile disclosure/sidebar component, plus history/settings pages. It currently says account page/layout and shell, but does not name the shared shell export or prop contract. Before parallel work, have Lane 3 publish a minimal `AccountShell` interface (destinations, active route, sign-in/return state, content slot) and error/loading conventions. Lane 1 owns only `/account/people/**` and `/account/dates/**`; Lane 2 only `/account/images/**` and `/account/drafts/**`. Parent alone owns `FlowHeader`/global menu and builder handoffs. This avoids each lane making its own navigation or page wrapper.

2. **Define one Settings/reminder-preferences contract.** Lane 3 owns the preference record and `/api/account/preferences` read/write, including timezone, verified reminder destination state, and account-wide pause. Lane 1 owns per-occasion consent and outbox dispatch. Add to the frozen contract the exact shared service/read method and version fields Lane 1 will consume; dispatcher must read current pause, verified destination, and timezone immediately before claim/send, while Lane 3 settings writes atomically update those same canonical fields. Per-occasion pause/opt-in remains in Lane 1. Define destination changes as pending verification until confirmed, and ensure re-enable requires verified destination. Avoid a second “global pause” field in reminder docs.

3. **Make retained private assets a separate durable lifecycle.** The current Studio source, generation, and design objects have expiry (source/generation/design records are not permanent library records; accepted design has its own finite window), private object keys, and deletion cascades. Explicit “Save for later” must create a library-owned immutable object/version or otherwise extend the exact source and required dependencies transactionally; it must not merely pin an expiring Studio ID. Specify whether saving a source keeps only the normalized source or also the generated/composed derivatives, how each library asset is counted against quota, and what happens when a source is removed while a derivative is saved. Failed object copy or metadata commit must not show success. Retention extension is only on explicit save; unsaved Studio objects retain the current cleanup TTL and grants.

4. **Add safe ownership for a guest-generated cover.** Current `POST /api/generate-cover` is guest-accessible and returns `cacheId` plus `imageUrl`; the cached record is not UID-owned. Lane 2 must not let a signed-in user claim arbitrary `cacheId` or submit/fetch the image URL. Add a server-created, unguessable, short-lived save capability tied to the exact generated result (or a separate server-side pending-result record), preserved locally through sign-in and redeemed only after verified auth. On redemption, atomically bind/copy that result into the owner’s library, make retries idempotent, and reject expired, fabricated, already-claimed-by-another-owner, or unavailable cache records. Let the sender continue guest checkout if sign-in/save is canceled or unavailable; no implicit library write. Keep prompt metadata private and do not put capabilities in URLs/analytics.

5. **Specify cancellation and account-switch behavior for the builder handoff.** The existing Upload Studio sends an accepted design ID through `/new?uploadDesign=…`; `app/preview/entry/client.tsx` already validates the design against the signed-in UID and can record private recovery. Define a handoff state machine for pending, accepted, canceled, expired/revoked, and account-changed states. Cancel/back before acceptance must return to the existing draft with note/address intact and must not clear or replace its cover; after acceptance, canceling the picker must leave the user on the ordinary review flow with the selected cover and no accidental reset. A UID change must clear private pixels/selections while preserving non-sensitive note/address work and offering re-authentication or a catalog-front choice. Strip the query capability after processing and never leave a stale URL that can auto-select on refresh. Parent owns these builder changes; Lane 2 only exposes a stable library/Studio handoff contract.

6. **Tighten the remaining shared-file ownership.** The route/file table lists parent-owned picker and builder integration, but the Lane 2 ownership row includes `app/create/upload/page.tsx`, `components/upload/UploadStudio.tsx`, and all `app/api/upload/**`. Prefer a thin Lane 2 adapter/new library endpoints and only named UI seams in the existing Studio; Lane 2 should not own or broadly edit the established upload API implementation. Existing SPRINT-0022 source/grant/acceptance logic is a regression-sensitive security boundary. Explicitly reserve it to parent unless a minimal endpoint extension is reviewed and assigned.

7. **Resolve the “one-off tomorrow” reminder edge before release.** The approved design defaults to an opt-in 14-day reminder; the A draft adds a separate “tomorrow” option for events under 14 days. That is a new behavior absent from the design spec and needs explicit coordinator approval or removal. Preserve calendar arithmetic and leap/DST behavior, but do not add an alternate lead time by implication.

## Suggested acceptance additions

- Browser test every account route within the same Lane 3 shell at 320/390/768/1024, with a deep-linked Lane 1 or 2 page, refresh, Back, signed-out return and account switch; assert no duplicate shell/navigation.
- Save a guest-generated result after sign-in using only the one-time capability; test forged cache ID/URL, capability expiry, another UID redemption, retry after object-copy timeout, canceled sign-in, and guest checkout continuation.
- Use injected time to expire the original Studio source and design while confirming a deliberately saved library asset still opens; verify unsaved objects clean up on schedule and deleting a source follows the documented derivative policy.
- Pause globally in Settings while an outbox item is leased, change timezone/destination, then resume; assert the dispatcher uses the canonical current preference and no stale/duplicate send occurs.
- Cancel/back from each upload handoff state and switch UIDs mid-preview; assert note/address persist, private pixels clear, and no stale upload selection reaches review or checkout.
