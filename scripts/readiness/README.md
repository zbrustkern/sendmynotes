# Account readiness tooling

Run from the release checkout. Every cloud command requires an explicit environment name **and** matching project id. `SMN_GCLOUD_BIN` may point to the installed Google Cloud CLI. Authentication tokens remain in process memory; evidence contains references and presence flags, never secret payloads.

- `node scripts/readiness/preflight.mjs staging sendmynotes-staging report.json` reads runtime identity/config presence, bucket policy, collection-specific indexes, secret-container presence and regional jobs. A successful inventory is not a release approval or runtime storage proof.
- `node scripts/readiness/provision.mjs plan production sendmynotes-2a417 report.json` previews additive bucket, scoped runtime IAM, empty secret containers and indexes. `apply` executes the same resource preparation. Existing indexes are retained; unsafe existing bucket policies stop the run. No application rollout or job activation occurs.
- `node scripts/readiness/seed-secrets.mjs plan production sendmynotes-2a417 report.json` checks enabled versions and IAM. `apply` generates only missing initial random key versions and grants the verified runtime/App Hosting service identities access. Existing keys are never rotated. Review config references before rollout; new production signing keys invalidate sessions/tokens previously signed with the legacy fallback.
- `node scripts/readiness/scheduler.mjs plan staging sendmynotes-staging report.json` inventories jobs across locations and reports desired authenticated POST schedules. It never creates, changes or activates jobs. Existing staging upload cleanup is retained, including its existing cadence. New jobs remain an explicit operational gate; do not mistake a plan for deployed jobs.
- `node scripts/readiness/run-tests.mjs` runs the merge/payment/recovery suites with isolated synthetic storage, mock email configuration and blocked external transports. Optional arguments select test basenames. `npm run test:account` runs the account suite. Never run fulfillment scripts as a check.

App Hosting secret references use immutable version 1 in this candidate. Production and staging use different project-local secrets and private buckets. Reminder delivery is explicitly false; no sender identity is invented. A verified sender, controlled inbox/unsubscribe proof, operators, backlog review and separate activation authorization are required. [Firebase configuration reference](https://firebase.google.com/docs/app-hosting/configure).

Cloud Scheduler cannot create a job directly in PAUSED state (`state` is output-only). Safe creation/activation must be reviewed after dry-run storage fixtures; the inventory tool intentionally does not create then race to pause a job. [Cloud Scheduler Job reference](https://docs.cloud.google.com/scheduler/docs/reference/rest/v1/projects.locations.jobs).

Production Scheduler API availability is checked separately from application readiness. Enabling an API alone does not establish a working authenticated schedule. The first application rollout can keep reminders disabled, but cleanup schedules and operator ownership must be accepted or explicitly deferred in the release decision.
